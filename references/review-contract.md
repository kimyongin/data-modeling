# 모델 JSON과 공통 뷰어 계약

새 사례는 [모델 JSON 작성 안내](model-json.md)의 `schemas/model-1.0.0.schema.json`을 따라 직접 작성하고 공통 뷰어에서 연다. 기본 산출물은 `.model.json`이며 HTML 생성은 필요 없다. [직접 작성 예제](example-model.json)에 체크섬·렌더러 핀·SQL이 없는 완전한 문서가 있다.

기본 문서는 format=data-modeling-model, format_version=1.0.0, review를 갖는다. verification과 build_metadata는 선택이며 없으면 미실행·생성 정보 없음으로 표시한다. 아래 표는 review 안의 업무 필드다. 직접 작성/스킬 생성/파일 공유 모두 같은 계약을 따른다. 실행 검증용 중간 입력의 차이는 별도 절에서만 설명한다.

## 기본 모델 JSON의 review 필드

| 필드 | 형식·의미 |
|---|---|
| schema_version, review_profile | 필수. schema_version은 1.0.0, 새 설계의 review_profile은 standard. 기본 모델에는 renderer_version·체크섬·실행 코드가 필요 없음 |
| title, summary | 제목, 설계 목적 문자열. 필수 |
| initial_entity | 선택. 첫 화면에서 설명·샘플을 보여줄 엔터티 ID. ERD는 전체 맞춤을 유지 |
| design_summary | 선택. 실제 설계가 뒷받침하는 핵심 선택을 설명하는 문자열 배열 |
| review_points | standard 필수(해당 없음은 빈 배열), compatibility 선택. 아래 검토 쟁점 형식. 전역 ID 중복 금지 |
| reading_guide | 선택. 이 업무 사례에서 먼저 볼 영역·정보와 확인할 질문을 쉬운 문장으로 작성 |
| process | standard 필수, compatibility 선택. `{skill, steps:[실제 수행한 절차 문자열...], scope?}`. steps는 비어 있지 않아야 함. 누락 시 기본 절차와 실제 수행 내역 미기재 경고를 표시하며 조사·실행을 했다고 단정하지 않음 |
| level, review_status, scope | 모델 수준, 합의 상태(기본 초안), 범위 문자열 |
| requirements | `{id, text, ...}` 배열. 필수 |
| sources | `{id, title, url 또는 location, kind, checked_at, version, claim, limitation}` 배열. kind는 사실/해석/미확인/충돌 등을 표시 |
| decisions | `{id, title, rationale, alternatives, requirements:[], sources:[]}` 배열 |
| assumptions, limitations | 설명 문자열 또는 `{id, title, detail, impact, ...}` 배열 |
| domains | 선택. `{id, name, description?, entities:[엔터티ID...]}` 배열. 업무별 검토 대상 집합. 여러 영역에 중복 소속 가능. `all`은 전체 보기용 예약 ID이므로 사용하지 않음 |
| entities | 엔터티 배열. 필수. 각 항목 `{id, name, grain, description, group?, short_description?, example?, review_question?, sample_label_columns?, insights?, requirements:[], sources:[], columns:[], rows:[]}` |
| entities[].columns | `{name, label?, type, key, nullable, description}`. standard에서는 name·label·type·key·nullable·description 필수. key 예: PK, FK, UQ, PK/FK. label은 업무용 이름이며, 영문 name과 원 타입은 그대로 보존. 복합 키·범위·인덱스·이력 규칙은 description/decisions로 보충 |
| entities[].rows | 컬럼명을 키로 하는 샘플 행 객체 배열. 뷰어에 표시할 샘플이며 별도 실행 검증을 한다면 같은 행을 사용 |
| relationships | 관계 배열. 필수(없으면 빈 배열). `{id, name, from, to, foreign_key?:boolean, explanation?, rationale?, title?, rule, enforcement, requirements:[], sources:[]}` |
| 관계 양끝 from/to | `{entity:엔터티ID, columns:[필드명], cardinality:"0..N"}`. cardinality는 **해당 끝에 위치한 대상 수**. 자식→부모 관계라면 from에 0..N, to에 1 등이 온다. columns 순서는 복합 참조 필드 대응 순서. FK 아닌 논리 관계는 `foreign_key:false`와 enforcement에 명시. 물리 FK는 `foreign_key:true`로 지정하고 양끝 열을 같은 수·대응 순서로 작성. 명시적인 compatibility 입력에서만 enforcement/rule에 FK·FOREIGN KEY·외래키가 명시된 관계만 FK 열 보완에 사용하며 모든 논리 연결을 FK로 만들지 않음 |
| scenarios | `{id, title, requirements:[], entities:[], explanation:{situation,expected_behavior,why_it_matters}, sample_refs?, sample_note?}` 배열. SQL·expected·실행 결과 없이 작성 가능 |

엔터티·요구사항·관계·시나리오·근거·결정·업무 영역 ID는 전체에서 중복되지 않게 하고 영문자로 시작해 영문·숫자·밑줄·하이픈으로 작성한다. 예: `R-01`, `E-01`, `project`, `REL-01`, `S-01`. 연결 필드의 ID는 실제 존재해야 한다.

## 업무 담당자가 이해할 수 있는 설명 필드

새 보고서는 전문 용어를 아는 독자를 가정하지 않는다. 엔터티 `description`은 어떤 정보를 왜 관리하는지, `grain`은 표 한 줄의 의미, `example`은 실제 샘플의 인물·코드·금액에 맞는 예, `review_question`은 업무 담당자가 판단할 질문이다. 설명은 문자열이다. `columns[].label`은 비어 있지 않은 업무용 이름이며 속성·샘플 표에서 영문 이름과 함께 표시한다. 관계의 `explanation`에는 연결의 업무 이유와 예를 쓴다.

시나리오 `explanation = {situation, expected_behavior, why_it_matters}`는 세 개의 비어 있지 않은 문자열이다. 업무상 기대 동작을 업무 확인 결과로 보여준다. 전체 설명과 실행 자료는 재생성용 원본 파일에 보존하며 SQL·원시 결과는 HTML에 넣지 않는다. 기대값을 그대로 문장으로 되풀이하지 말고 숫자와 거부 동작이 업무에 무엇을 뜻하는지 설명한다. `result_columns`와 expected 배열은 기본 모델 JSON의 필드가 아니다. 실제 SQL 실행을 별도로 검증할 때만 내부 입력에 작성한다. 실패·미실행에도 예상 동작은 설명할 수 있지만 실제로 달성한 결과처럼 쓰지 않는다.

출처 `reading_note`는 이 자료를 읽는 업무상 이유와 한계를 짧게 설명한다. 설계 결정에는 `example`, `review_question`, `technical_note`를 추가할 수 있다. 쉬운 설명을 먼저 읽고 기술 정의를 이어서 볼 수 있도록 작성한다. 모델의 원래 필드는 보존한다. SQL·원본 실행 결과는 재생성 파일에만 남기고 HTML이나 모달에 넣지 않는다.

요구사항의 전체 범위·전제 항목은 입력에 맞는 읽는 순서를, 참조의 용어 안내는 공통 용어 설명을 제공한다. ERD에는 PK/FK·개수 범례를 표시한다. 명시적인 compatibility 입력은 일부 설명이 없어도 동작하지만 생성기가 업무 의미나 예시를 임의로 보완하지 않는다. 특히 미작성 설명과 실행 보고서 없음은 그대로 알린다.

## 분량과 검토 기록

[설명 작성](report-writing.md)에 따라 역할·선택·공통 전제를 분리하고 같은 문장을 여러 필드에 복제하지 않는다. 필수 필드를 채우기 위해 가짜 위험·질문을 만들지 않는다. 검토 강도는 [설계 검토](design-review.md)의 복잡도 기준으로 정한다. `extensions.modeling_review`는 독립 1.0.0 계약이며 현재 모델 형식/필수 UI 필드를 변경하지 않는다.

## 엔터티별 설명

`entities[].insights = {purpose, tradeoff, risk, decision_ids:[], source_ids:[], scenario_ids:[]}`. 세 설명은 비어 있지 않은 문자열로 작성하며 참조 ID는 해당 결정·출처·시나리오에 실제 존재해야 한다. 같은 일반 문장을 반복하지 말고 엔터티의 업무 문제·선택의 대가·미결 위험을 설명한다. 자동으로 속성 수나 관계 목록을 문장으로 바꾸지 않는다. 해석이 없으면 미작성이라고 표시하고 raw description을 인사이트처럼 대체하지 않는다.

해석은 보고서 작성 시 판단한 내용이다. 검증 가능한 사실, 설계 추론, 미확인 위험을 혼동하지 않도록 쓴다. 전체 해석과 직접 연결된 조사·검증의 필요한 설명은 모델의 설명 하위 탭에서 읽는다. 내부 참조는 코드: 타이틀의 텍스트로 표시하고 미리보기 모달이나 이동 버튼을 만들지 않는다. standard 입력은 엔터티별 insights·업무 예·검토 질문·항목 설명을 반드시 작성한다. 미작성을 유지하는 compatibility 입력은 명시적 허용이 필요하다.

## 선택적인 내부 실행 검증

이 절만 schemas/review-1.0.0.schema.json의 중간 입력을 사용한다. renderer_version은 현재 생성기에 고정하고 sqlite/expected 또는 expect_error/query 등 실행 자료를 내부 입력에 작성한다. 기본 모델 작성에 이 자료를 강요하지 않는다. 실행 후에도 최종 결과는 JSON이다.

```bash
.venv/bin/python <skill-dir>/scripts/verify_sqlite.py review.json --output verification.json
.venv/bin/python <skill-dir>/scripts/build_model.py review.json --verification verification.json --output case.model.json
```

각 시나리오는 **새 인메모리 DB**에서 DDL→공통 샘플 행→setup_sql→query 순서로 실행된다. 공통 데이터의 엔터티 순서는 참조 부모가 먼저 오게 한다. setup_sql에는 시나리오를 위한 추가 입력·변경을 넣고 query에는 단일 검증 SQL을 넣는다. 결과 행은 배열의 배열로 expected와 비교한다. `ORDER BY`를 쓰거나 `unordered: true`를 지정한다. unordered 비교도 중복 개수를 보존한다. params는 위치 기반 바인딩 값 배열이다.

- 조회 예: `expected: [["P1", 2], ["P2", 0]]`.
- 오류 예: `expect_error: "SQLITE_CONSTRAINT_FOREIGNKEY"`. query가 해당 무결성 오류로 실패해야 통과한다. 준비 단계의 오류나 구문 오류로는 통과하지 않는다.
- 오류 보고서는 원시 `error_code`와 비교용 `error_category`를 보존한다. SQLite 버전별 `ON DELETE RESTRICT`의 표준 FK 오류와 PK 중복을 각각 FOREIGNKEY·UNIQUE로 정규화한다. 다른 사용자 정의 트리거를 FK로 간주하지 않는다. 확장 오류 코드를 제공하지 않는 구형 Python에서는 사용자 정의 트리거 오류 종류를 확정할 수 없으므로 정확한 TRIGGER 기대값 검증에는 Python 3.11 이상을 사용한다.
- `expected`와 `expect_error`는 동시에 지정하지 않는다.
- 변경 성공 예: setup_sql에 변경을 넣고 query의 SELECT로 변경 후 상태를 검증한다. 변경문의 빈 반환값만으로 업무 결과를 검증했다고 하지 않는다.
- query가 없는 시나리오는 미실행이다. 실패·미실행·시나리오 없음 중 하나라도 있으면 실행기는 종료 코드 1을 반환하고 보고서를 남긴다.
- 검증 결과에는 입력 파일 SHA-256이 포함된다. 입력이 바뀌면 다시 검증한다. 렌더러는 오래된 보고서와 다른 시나리오의 보고서를 거부한다. 해시는 입력 대응 확인용이며 보고서의 독립적 진위를 보장하지 않는다.

SQLite는 대상 DB의 타입·잠금·동시성·트리거·배열·RLS 등과 같지 않다. 샘플용 이식 DDL과 실제 대상 DDL을 구별한다. 정확한 금액 검증은 최소 화폐 단위의 정수 또는 적합한 별도 decimal 실행기를 사용한다. 파일 연결과 임의 PRAGMA는 차단하고 각 시나리오의 연산량을 제한하지만 보안 샌드박스를 대신하는 실행기는 아니다. 직접 검토한 로컬 샘플 SQL만 사용한다.

다른 DB·문서·그래프 검증은 적합한 도구로 수행한다. 필요하면 동일한 보고 형식(`engine`, `scope`, `input_sha256`, `executed_at`, `results:[{id,status,actual,...}]`)으로 어댑터를 작성한다. 실제로 실행한 결과만 pass로 표시한다. 수동 검토는 실행 보고서로 꾸미지 말고 시나리오 설명과 limitations에 방법·결론을 적는다.

## 기존 공통 뷰어의 화면 계약

문서 전체는 100dvh에 고정하고 body/html 스크롤을 제거한다. 상단 제목·검토 상태와 개요/스펙/모델/참조의 4개 탭, 하단 검증·미확인 요약은 고정한다. 긴 정보는 탭 본문·목록·표 안에서 스크롤한다. 전체 내용과 관련 근거의 필요한 설명은 탭 본문에서 읽으며 내부 참조는 일반 텍스트로 표시한다.

### 탭 안내

각 상위 탭의 목적과 내용을 짧고 구체적인 한 문장으로 설명한다. 선택한 탭의 설명은 상단 헤더의 보고서 제목 바로 아래에 `메뉴 이름 - 설명` 형식의 작은 글씨로 표시하고 탭 전환에 맞춰 갱신한다. 본문/탐색 영역에는 중복하지 않고 제목/주 메뉴와 분리된 전역 설명 행도 만들지 않는다. 제목·동작 설명만 반복하지 않는다. 모델 상세의 속성·설명 하위 탭은 각 패널 상단에 별도의 목적·내용을 표시한다.

설명은 생략·말줄임하지 않고 화면 폭에 따라 줄바꿈한다. 얇은 안내 높이를 포함해 작업 공간을 계산하며 문서 스크롤·버튼 잘림·불필요한 ERD 축소를 피한다. 현재 상위 패널은 안내와 접근성 설명 관계를 연결한다. 목록을 고를 때 현재 탭 안내는 유지하고 상위 탭을 바꾸면 그 탭의 안내로 갱신한다.

### 탭별 구성

| 탭 | 탐색 | 전체 내용 표시 위치 |
|---|---|---|
| 개요 | 이동 버튼 없음 | 문제·전체 구조·사용 예·핵심 미결 사항. 내부 스크롤 없이 읽는다. |
| 스펙 | 요구사항 검색 목록, 공통 사항, 전체 범위·전제 | 요약 → 설계안과 예시 → 남은 결정 |
| 모델 | 이 탭에만 업무 영역 선택기 | 중앙 ERD와 열기/닫기 샘플 드로어, 오른쪽 속성/설명 |
| 참조 | 개별 근거 자료·제작 과정·용어 안내를 한 검색/스크롤 목록으로 선택 | 오른쪽에 선택한 항목의 전체 내용/한계/원문 또는 제작 과정/용어 안내 |

결정·쟁점의 `requirements`로 실제 관련된 것만 같은 요구사항 본문에 표시한다. 동일 원본을 여러 관련 요구사항에서 읽으며, 요구사항이 여러 개이거나 없는 결정·쟁점은 공통 항목에도 제공한다. 특정 쟁점과 특정 설계안 사이의 인과관계는 임의로 생성하지 않는다. 내부 연결은 텍스트로 보존하고 목록에서 고른 요구사항 본문에 관련 내용을 함께 표시한다. 연결이 없는 항목을 숨기지 않는다.

스펙 요구사항 본문은 요약·설계안·남은 결정으로 구성하고 확인 목록·실행 상태를 나열하지 않는다. 모델 탭의 왼쪽 선택기와 오른쪽 설명이 선택 업무 영역의 상황·기대 동작·관찰 결과와 ERD·샘플 연결을 담당한다. SQL·예상/실제 비교 표·원시 JSON·상세 펼치기는 표시하지 않는다. HTML 내장 데이터에서도 실행 SQL·DDL·원시 오류·결과 배열은 제거한다. 원본 입력과 보고서의 해시 대조는 제거 전에 수행하고 원본은 변형하지 않는다.

개요는 작성된 overview의 문제·연결 그림·대표 사용 예·핵심 미결 사항을 표시한다. 기존 summary/scope/design_summary 전체는 스펙의 범위와 전제에서 보존한다. 내용 잘림·축소·말줄임으로 한 화면을 맞추지 않으며 3개 데스크톱 해상도에서 직접 읽는다. 새 개요에 제작 절차·용어·검사 건수·전체 쟁점을 반복하지 않는다. 참조는 근거 자료 각각·제작 과정·용어 안내를 한 목록에서 선택하며 검색·선택·목록 스크롤과 항목별 본문 스크롤을 보존한다.

모델의 탐색기와 오른쪽 상세는 다른 탭에서 공간을 차지하지 않는다. 목록 선택은 해당 본문을 직접 갱신하며 내부 참조 텍스트는 이동·모달을 만들지 않는다. 설명·선택지·대안·관찰 결과는 해당 탭 본문에서 읽는다. 탭별 검색·선택·목록/본문 스크롤과 ERD 카메라를 보존한다. 상위/하위 탭은 방향키/Home/End와 선택 상태를 제공하고 외부 원문만 안전한 새 탭으로 연다.

### 내부 참조 표기

참조 텍스트·목록 항목·상세 제목은 공통 포맷터로 코드: 타이틀을 표시한다. title이 없으면 name, 요구사항 text 순으로 사용한다. 내부 참조는 클릭되지 않는 텍스트로 제공하고 필요한 설명·선택지·대안은 현재 본문에 둔다. 외부 원문만 참조 탭에서 새 탭 링크로 제공한다.

### ERD와 모델 상세

`domains`는 업무별 검토 대상 집합이며 `entities[].group`은 공통/소스별 시각 구분이다. domains가 없으면 전체 구조만 제공한다. 영역 선택 시 primary=domain.entities, context=primary가 직접 참조하는 외부 부모를 한 단계만 보완하고 visible=primary∪context의 양끝이 보이는 관계를 표시한다. context를 재귀 확장하지 않는다. 전체 보기는 모든 공통·전용 엔터티·관계를 복원한다. 연결 대상은 키를 보존한 점선 상자로 구분하고 현재 오른쪽 패널에서 전체 정의를 확인한다.

관계 기반 Graphviz dot의 좌우 흐름을 기본으로 가까운 연결 묶음을 배치한다. 공통/소스별 라벨·경계를 유지하면서, 여러 외부 영역을 연결하는 허브를 분리하고 같은 소스 안의 직접 연결 요소들을 가까운 영역으로 묶는 후보와 원래 소스 그룹 후보를 비교한다. 한 허브에 붙은 단일 동반 엔터티는 함께 둘 수 있지만 많은 병렬 가지를 다시 큰 외곽으로 묶어 공간을 벌리지 않는다.

병렬 그룹·동일 부모의 가지는 제한된 열 수의 짧은 행으로 나누고, 이웃 행 사이에 긴 보조 체인을 강제하지 않는다. 연결선 끝을 항상 동서 방향으로 고정하지 않고 가까운 경계로 연결한다. 간격·그룹 여백을 줄인 꺾은선/곡선 후보를 비교한다. 배치에만 사용하는 보조 순서는 실제 관계선·상세·개수에 포함하지 않는다.

후보는 화면 맞춤 배율, 엔터티 바운딩 박스 면적/전체 면적인 점유율, 실제 관계 경로 길이를 엔터티 크기로 정규화한 값을 함께 평가한다. 가로 비율은 완만한 선호 조건이며 글자 크기·근접성을 희생해 폭만 늘리지 않는다. 측정용 SVG는 화면 밖 숨김 컨테이너에서 계산하고 즉시 제거한다. 엔터티가 겹친 후보는 제외한다. 선택된 배치는 영역별로 캐시하고 엔터티 선택·탭·크기 변경 때 재배치하지 않는다.

처음에는 전체 엔터티·관계를 화면에 맞춘다. ERD는 단일 PK·FK 보기이며 엔터티 이름과 PK/FK 속성만 표시한다. 복합 FK 구성 열은 관계 정의에서도 보완하고 PK/FK 겸용 열은 한 번만 표시한다. 일반/UQ 전용 속성은 제외한다. 키 미정 상태를 임의 식별자로 대체하지 않는다. 선에는 양끝 카디널리티만 표시하고 REL-N은 관계 상세에만 보존한다.

오른쪽 속성 탭은 모델 설명·한 행의 의미·전체 속성 이름/키/원 타입/필수성/설명을 표시한다. 별도 관계 탭은 두지 않는다. 관계선 선택 시 설명에서 해당 관계를 만든 이유로 이동한다. 삭제 정책·복합 연결도 업무상 이유와 영향으로 설명한다. 설명 탭은 purpose/tradeoff/risk와 직접 관련된 근거·확인 결과의 설명과 참조 텍스트를 표시한다. 같은 메타데이터 반복을 해석으로 사용하지 않는다. 모든 본문은 끝까지 내부 스크롤하며 별도 전체 정의 모달을 만들지 않는다. 상단의 중복 “속성 정의” 버튼은 제공하지 않는다.

도형 선택은 강조·속성·샘플만 갱신하고 카메라·배치·SVG를 보존한다. 드래그·휠·배율 버튼으로 수동 이동/확대한다. 초기 표시·명시적인 영역 변경·전체 보기만 화면 맞춤을 수행한다. 탭 전환으로 영역·선택·배율·위치를 초기화하지 않는다.

ERD 내부에 user-select 방지와 기본 selectstart/dragstart 방지를 적용하고 포인터 이동으로 팬을 처리한다. 속성·샘플·다른 탭은 선택 가능한 상태를 유지한다. 클릭과 드래그를 구분하고 드래그 후 선택·상세 전환을 억제한다.

ERD 오른쪽 아래 미니맵은 현재 영역의 엔터티/관계 배치를 간략한 도형으로 표시한다. 기본은 접힘이며 작은 “미니맵 열기” 버튼만 남긴다. 열면 닫기 버튼을 제공하고 aria-expanded/aria-controls와 키보드 조작을 지원한다. 영역·탭 전환에 열림/접힘 상태를 보존하며 토글 자체는 카메라·선택·SVG를 변경하지 않는다. 현재 보이는 범위를 프레임으로 겹쳐 표시하고 이동·확대·창 크기 변경 때 갱신한다. 클릭한 지도 좌표를 ERD 좌표로 변환하여 같은 배율에서 화면 중앙으로 이동한다. SVG의 실제 화면 변환(여백·종횡비 포함)을 반영하고 범위 프레임은 지도 경계와 교차하는 부분만 표시한다. 전체/업무 영역 전환 때 지도 원본도 교체한다. 지도 클릭은 엔터티 선택이나 그래프 재생성을 일으키지 않으며 뒤쪽 캔버스로 이벤트를 전파하지 않는다. 방향키·Enter 이동을 제공하고 복제 DOM ID/중복 포커스 대상을 만들지 않는다.

중앙 샘플 데이터 드로어에 모든 샘플 행과 긴 값을 생략 없이 표시하고 내부 수직/수평 스크롤과 고정 머리글·행 수를 사용한다. 긴 값은 줄바꿈한다. 샘플 모달·전체 N행 보기 버튼은 없다. 같은 엔터티의 탭 전환·창 크기 변경 시 표 스크롤을 보존한다.

### 재생성과 검수

CSS·JS·배치 엔진·타사 고지를 내장해 외부 CDN·서버 없이 동작한다. textContent/XML 및 내장 JSON 이스케이프, 검증 보고서 해시 대조와 입력 검증을 유지한다. 실제 검증·샘플 시뮬레이션·미실행을 구별한다.

1440×900·1920×1080·1366×768에서 개요의 큰 그림과 한 화면 노출, 스펙의 공통 항목 우선 순서·원문 보존, 참조 탭 이름, 내부 이동 버튼·참조 모달 없음과 안전한 외부 원문 링크를 확인한다. ERD 제목을 좁은 패널에서도 말줄임 없이 읽고 설명의 섹션별 역할·선택과 영향·관계 이유·남은 판단·실제 확인 결과가 구분되는지 직접 읽는다. 기존의 정확한 업무/확인 사항 범위·모든 PK/FK·일반 속성·전 행 샘플·실패/미실행·오프라인·키보드·미니맵·양쪽 경계·카메라·탭별 선택/스크롤·긴 값·문서 스크롤 없음도 회귀 검토한다.

## 재실행 가능한 회귀 점검

버전·무결성·입력 거부·명시적 이전·동일 바이트 재생성은 아래 검사로 확인한다.

```bash
.venv/bin/python <skill-dir>/scripts/audit_versioning.py --manifest manifest.json --output versioning-checks.json
```

입력 거부·기대값 대조·오류 단계 구별·오래된 검증 보고서 차단은 포함된 프로젝트 예시로 점검한다. 스키마 검증을 위해 전용 환경의 고정 의존성이 필요하다.

```bash
.venv/bin/python <skill-dir>/scripts/audit_review.py <skill-dir>/references/example-review.json --output audit-validation.json
```

기본 회귀 점검은 모델 JSON만 만든 뒤 기존 공통 뷰어에서 확인한다. manifest에는 사례명, 원본 input, 생성할 model, 선택 verification, allow_compatibility를 작성한다. 직접 작성 입력이면 verification은 null이다. 별도 실행 검증용 중간 입력만 외부 실행 보고서를 연결한다.

```json
[{"name":"사례명","input":"/absolute/source.json","model":"/absolute/case.model.json","verification":null,"allow_compatibility":false}]
```

```bash
.venv/bin/python <skill-dir>/scripts/audit_model_json.py --manifest manifest.json --output model-checks.json
node <skill-dir>/scripts/check_model_json.cjs manifest.json <existing-viewer.html> model-ui.json <skill-dir>/references/example-model.json
```

브라우저 점검에는 Node.js·Playwright·Chrome이 필요하고 PLAYWRIGHT_MODULE/CHROME_PATH로 경로를 지정할 수 있다. 설치되지 않았으면 확인했다고 보고하지 않는다. 이 경로는 사례 HTML을 생성하지 않는다. 기존 check_review_ui.cjs/check_review_transfer.cjs의 html manifest는 독립 HTML을 명시적으로 점검할 때 쓰는 유지보수 전용이다. 결과 JSON의 실패·오류·화면을 확인하며 성공 개수만으로 모든 도메인이나 시각 품질을 보장하지 않는다.

## 검토 쟁점과 요구사항 연결

`review_points = [{id,title,kind,question,options:[],recommendation,impact,entities:[],requirements:[],scenario_ids?:[]}]`. kind는 `decision`(업무 정책), `scope`(제외 범위), `verification`(실행 미검증)이다. 제목·질문·추천·영향은 비어 있지 않은 문자열, 선택지는 비어 있지 않은 문자열 배열이다. 관련 ID는 존재해야 한다. 추천은 사용자 승인 상태가 아니며 현재 제안·미확정으로 표시한다. 새 보고서는 엔터티별 위험을 이 쟁점 목록과 대조해 모두 다룬다.

기존 입력에 쟁점 목록이 없거나 일부 엔터티가 연결되지 않았으면 그 엔터티의 위험을 ‘분류가 필요한 기존 위험’으로 모은다. 생성기가 선택지나 결론은 작성하지 않는다. 하단의 검토 쟁점 수는 이 중앙 목록의 수이고, 전제·일반 제한은 별도로 표시한다. 스펙에는 명시된 모델·결정·쟁점을 연결하고 확인 시나리오는 모델 탭의 업무 확인으로 연결한다. 연결 없음도 보존한다.

## 속성과 샘플의 우선순위

`entities[].short_description`은 속성 탭의 한 문장 역할 설명이다. 전체 description·example·review_question은 설명 탭에서 읽는다. 항목을 모달이나 접힌 카드로 옮기지 않는다. `sample_label_columns`는 참조 행의 업무용 이름을 만들 실제 열 이름 배열이다. 생략 시 name/title/code 중 존재하는 첫 열을 사용한다. 원래 값은 `.sample-value`에 그대로 표시하고, 완전한 FK 대응으로 정확히 한 행을 찾은 경우에만 이름을 `.sample-reference`에 보완한다. 복합 FK는 전체 열로 일치를 확인하며 첫 연결 열 옆에만 표시한다. 이름을 만들 때 참조 한 단계를 추가로 확인할 수 있으며 순환을 재귀 확장하지 않는다.

업무 설명용 데이터와 장문·스크립트 문자열 시험은 별도 입력으로 관리한다. 줄 수를 맞추려고 의미 없는 행을 늘리지 않고, 표가 긴 테스트 문자열 한 줄로 채워지지 않는지 실제 높이를 확인한다. 원래 값·전체 행 접근과 탭 왕복의 스크롤 보존은 유지한다.

## 업무 영역별 요구사항 확인 계약

`scenarios[].entities`는 중복 없는 실제 엔터티 ID 배열이다. 생략한 기존 입력도 전체 확인 목록에 연결 미작성으로 제공한다. 확인 사항은 원본 ID별 한 번만 표시하고, 요구사항·insights·그룹명으로 관련 모델을 자동 추측하지 않는다.

`sample_refs = [{entity, key:{pkColumn:value,...}}]`는 시나리오에 명시한 모델의 기본 행만 가리킨다. 전체 PK가 필요하고 null·빈 key·없는 행·여러 행 일치는 거부한다. 엔터티가 PK를 정의하지 않았으면 행 연결을 작성하지 않는다. 추가 입력/변경 결과 행을 기준 데이터로 위장하지 않고 sample_note로 설명한다.

`observation`, `sample_note`는 선택적인 비어 있지 않은 문자열이다. observation은 결과가 pass일 때만 공개 관찰 문장으로 사용한다. expect_error에 대응하는 구체 거절 이유는 정확한 오류 증거가 있을 때만 표시한다. 실패·setup 오류·not_run에서는 observation을 숨기고 실제 상태를 표시한다. 기대/실제 대조와 오류 검사는 내부 실행 파일에 유지한다.

모델 오른쪽 설명은 왼쪽에서 선택한 확인 사항의 실제 상태·관찰 결과·관련 요구사항과 모델을 텍스트로 설명한다. 설계 이유와 실제 확인 결과를 구분하고 동일한 결과를 다른 패널에서 반복하지 않는다. ERD는 항상 보이고 기본 샘플은 중앙 샘플 데이터 드로어에서 읽는다. 확인 사항 범위가 정해진 뒤 ERD의 관련 모델 선택과 샘플 드로어 전환은 SVG·배율·위치·영역을 바꾸지 않는다. 확인 사항 범위는 명시한 관련 모델과 직접 참조 대상으로 제한하며 전체 구조는 도구 모음의 전체 보기로 복원한다. 해당 영역에 연결한 예시가 없으면 충족/통과를 선언하지 않는다. 모델·관계·샘플 강조는 실제 관계 및 정확히 연결한 행만 대상으로 한다. 도메인별 예시 선택과 탭/스크롤 상태를 보존한다.

## 스펙의 서술 필드

`requirements[].design`과 `example`은 선택적인 비어 있지 않은 문자열이다. design은 관련 결정과 실제 모델에 근거해 작성한 설명이며, 생성기가 엔터티 이름으로 문장을 추측해 조립하지 않는다. 문단과 같은 본문의 설계 이유·대안을 읽고, 근거 코드는 일반 텍스트로 확인한다. 기존 입력은 연결된 결정의 rationale로 대체하고 내용이 없으면 미작성 상태를 유지한다.

`review_points[].summary`와 `decisions[].summary`는 선택적인 비어 있지 않은 문자열이다. summary는 원문의 의미·선택지·범위·영향을 유지한 짧은 설명이다. 원본 질문·선택지·rationale·alternatives는 재생성 입력에 보존하고 본문에서는 이유·대안·선택지를 이동 없이 읽는다. 본문에는 요약→설계안/예→남은 결정을 한 열로 배치하고 반복 경고·화살표·카드별 필드 나열은 표시하지 않는다.

## 통합 모델 탐색과 서술 계약

`requirements[].design_points`는 선택적인 비어 있지 않은 문자열 배열이다. 규칙이 작성되어 있으면 `design` 문단과 중복 표시하지 않고 불렛으로 제공한다. 예시는 별도 짧은 문단으로 유지한다. `relationships[].rationale`는 선택적인 비어 있지 않은 문자열이며 관계 생성 이유를 설명한다. 없으면 이유 미작성으로 표시하고 카디널리티 설명으로 대체하지 않는다.

모델 오른쪽의 하위 탭은 속성/설명 두 개다. 관계선은 설명의 해당 관계 이유를 선택한다. 방향·개수·열 매핑·물리 제약 목록을 관계 설명 섹션에서 반복하지 않는다. 모델/관계의 원본 정의는 입력 파일에 유지한다.

왼쪽 탐색은 업무 영역/확인 사항 탭이다. 업무 영역은 전체 보기와 영역 목록, 확인 사항은 전체 시나리오의 중복 없는 평면 목록이다. 업무 영역별로 확인 사항을 복제하거나 요구사항 소제목으로 단계를 추가하지 않는다. 탭 선택 상태·목록 연결과 방향키/Home/End를 지원하며 탭별 스크롤을 보존한다. 확인 사항 선택은 원본 ID를 유지하고 관련 모델/정확한 sample_refs 행만 강조한다. 확인 사항 선택 시 scenario.entities를 중심으로 직접 참조 대상 한 단계만 보완한 ERD 범위로 전환한다. 전체 보기는 확인 사항 범위를 해제하고 모든 모델과 관계를 복원한다. 실제 결과는 오른쪽 설명에서 한 번만 표시하며 기본 샘플과 실행 후 결과를 구별한다.

## 다이어그램 전용 중앙 패널

중앙은 도구 모음과 ERD가 전체 높이를 사용하고, 샘플 드로어를 열면 하단에서 위로 겹쳐 표시한다. 확인 결과는 오른쪽 설명에 유지한다. 왼쪽 확인 사항 선택은 해당 관련 모델 범위로 전환하고 화면에 맞춘 뒤 오른쪽 설명을 연다. 같은 확인 사항을 다시 선택하거나 관련 모델·샘플·상세 탭을 고를 때는 배율·위치·SVG를 유지한다. 결과는 현재 업무 영역의 시나리오에 대한 것이며 선택한 엔터티 전체의 통과를 의미하지 않는다. 관계선은 같은 설명 안의 관계 이유로 이동한다. 관련 모델은 ERD에서 선택하고 샘플은 중앙 샘플 데이터 드로어에서 읽는다. 중복 이동 버튼은 두지 않는다. 속성·설명 전환과 샘플 드로어 열기/닫기는 ERD와 왼쪽 선택/스크롤을 바꾸지 않는다. 샘플 표의 전 행·긴 값·고정 머리글·가로/세로 내부 스크롤과 모델별 표 스크롤을 유지한다. 중앙 드로어에 표 공간이 충분하도록 너비를 조정하되 중앙 다이어그램의 가독성과 세 가지 데스크톱 해상도를 함께 확인한다.

## 양쪽 패널 너비 조절

모델 탭의 왼쪽 탐색/ERD와 ERD/오른쪽 상세 사이에 각각 드래그 가능한 경계를 둔다. 왼쪽·오른쪽 패널과 중앙 ERD의 최소 너비를 지켜 문서 스크롤이나 패널 겹침을 만들지 않는다. role=separator, 세로 방향·현재/최소/최대 너비와 제어 대상, 키보드 포커스를 제공한다. 좌우 방향키(Shift는 큰 폭), Home/End, Enter 또는 더블클릭 기본 너비 복귀를 지원한다. 포인터 캡처와 취소/해제 처리를 사용해 경계 밖에서도 드래그가 이어지고 완료 후 텍스트 선택 방지 상태가 남지 않게 한다. 너비를 바꾸어도 ERD 배율·위치·SVG·선택은 유지하고 미니맵 범위만 갱신한다. 상위/상세/탐색 탭 및 업무 영역을 바꾸어도 사용자 너비를 유지하며 창이 좁아지면 안전한 범위로 제한한다. 이 경계는 모델 탭에서만 표시한다.

## 확인 사항별 ERD 범위

`scenarios[].entities`를 직접 관련 모델로 사용하고 그들이 관계 정의에서 직접 참조하는 외부 대상을 한 단계만 연결 대상으로 추가한다. 연결 대상의 참조를 재귀 확장하거나 이름/요구사항으로 관련 모델을 추측하지 않는다. 보이는 모델 사이의 실제 관계를 모두 보존한다. 업무 영역과 확인 사항은 별도 범위 키로 레이아웃/카메라를 관리해 같은 ID나 과거 범위의 그래프를 재사용하지 않게 한다. 새 확인 사항 범위는 화면에 맞추며 같은 확인 사항의 재선택·모델/관계/샘플 선택·탭 왕복·패널 너비 변경은 해당 범위의 SVG/배율/위치를 유지한다. 모델 연결 미작성 예시는 그 상태를 알리고 좁은 범위를 지어내지 않는다. 도구 모음의 전체 보기는 필터를 해제하고 공통·전용 모델 및 모든 관계를 복원하며 선택한 확인 결과는 계속 읽을 수 있게 한다.

왼쪽과 오른쪽 너비 조절기는 각각의 패널을 대상으로 드래그·방향키·Home/End·Enter/더블클릭 기본 복귀를 지원한다. 한쪽을 조절할 때 반대편 패널 너비를 유지하고 중앙 최소 공간을 지킨다. 포인터 취소·모델 탭 외의 경계 숨김·화면 축소/확대 시 안전한 범위 제한과 사용자 너비 복원을 양쪽 모두 확인한다.

## 이동 없는 읽기와 개요

탭/각 목록/ERD 선택과 전체 보기·팬·줌·너비 조절을 주요 조작으로 유지한다. 다른 탭의 버튼을 반복하거나 같은 상위 탭으로 보내는 보고서 개요·스펙 읽기·본문의 중복 샘플 바로가기·관련 모델 이동·footer 바로가기는 제거한다. 내부 참조는 코드: 타이틀의 일반 텍스트로 표시하고 모달·클릭 이동을 만들지 않는다. 원래 참조 ID와 연결 메타데이터는 유지한다. 설계 이유·대안·미결 선택지·확인할 상황·예상 동작·실제 결과·기본 샘플 범위 등 판단에 필요한 설명은 해당 본문에 포함한다. 외부 원문 링크만 참조 탭에 남긴다.

ERD 도구 모음의 제목은 전체 텍스트를 줄바꿈해 표시하고 제목 행 높이를 내용에 맞춘다. 좁은 캔버스에서는 제목과 조작 도구를 위아래로 나누어 말줄임·가로 잘림을 피한다. 설명은 모델의 역할 / 설계 선택과 영향 / 관계를 만든 이유 / 남은 판단과 주의점 / 판단 근거 / 실제 확인 결과를 명확한 섹션으로 구분한다. 확인 사항을 선택했을 때는 그 결과를 먼저 읽고 나머지 설명을 이어서 읽는다. 구조·이유·예상 동작·실제 확인 결과를 구별하며 원래 설명은 축약 때문에 사라지지 않게 한다.

새 standard 입력에 필수인 `overview = {goal, diagram:{nodes:[{id,title,description?}], links:[{from,to,label}]}, connection, example:{situation,outcome}, pending, scope?}`는 직접 작성한 큰 그림이다. diagram은 1~8개의 핵심 업무 정보와 명시적인 연결을 담는다. node ID는 그림 안에서 유일한 안전한 문자열이고 연결 양끝은 실제 노드 ID여야 한다. 각 선의 label은 비개발자가 이해할 업무상 의미다. PK/FK·카디널리티·모든 속성을 넣어 ERD를 복제하지 않는다. 노드가 나열된 순서로 관계를 추측하거나 실제 없는 선을 그리지 않는다. 기존 structure:[{title,description}] 입력은 텍스트 설명으로 보존하고 연결을 지어내지 않는다. 모든 필수 텍스트는 비어 있지 않아야 한다. outcome은 모델이 지원하도록 설계한 사용 예이며 실제 통과 선언과 다르다. 실제 확인 결과는 모델 탭에서만 표시한다. 새 보고서는 관계 그림을 포함한 overview가 1366×768 한 화면에 읽혀야 하며, overview 자체가 없는 legacy 입력은 명시적으로 이전한 compatibility 모드에서 기존 summary/design_summary를 보존한다. 스펙 목록은 범위와 전제/공통 사항을 요구사항보다 먼저 둔다.

## 한 줄 상단과 본문 탐색

상단은 보고서 제목·주 메뉴·검토 상태를 하나의 바로 묶고, 전역 탭 설명 행이나 주 메뉴만의 별도 행을 만들지 않는다. 각 탭의 목적과 내용은 상단 헤더의 보고서 제목 바로 아래 `메뉴 이름 - 설명` 형식의 작은 한 문장으로 표시하고 탭 전환 시 바꾼다. 본문/탐색 패널에는 같은 안내를 반복하지 않는다. 참조는 왼쪽의 단일 스크롤 목록과 오른쪽 본문 두 열로 구성한다. 왼쪽에는 모든 근거 자료를 개별 항목으로 나열하고 제작 과정·용어 안내를 이어 둔다. 분류 메뉴·하위 탭·추가 출처 목록은 만들지 않는다. 전체 항목의 제목·내용을 검색하며 선택 상태와 목록 스크롤·항목별 본문 스크롤을 보존한다. 목록 버튼은 방향키 위/아래·Home/End와 선택 상태를 제공한다. 자료가 없어도 제작 과정·용어 안내는 제공한다. 개요의 연결 그림은 오프라인 SVG로 표시하고 화살표 의미를 텍스트로도 설명하며, 별도 이동/확대 버튼 없이 한눈에 읽게 한다. SVG의 DOM ID와 노드 클래스는 ERD·미니맵과 분리한다.

## 중앙 샘플 드로어

모델의 오른쪽 상세는 속성·설명 두 탭이다. 샘플은 중앙 도구 모음의 “샘플 데이터 보기/닫기”로 여는 하나의 드로어에만 표시한다. 기본은 닫힘이며 중앙 하단에서 위로 열려 캔버스 일부에 겹친다. 드로어는 중앙 패널 너비를 사용하고 문서 스크롤·모달·별도 오른쪽 샘플 탭을 만들지 않는다. 열기/닫기는 ERD SVG·배율·위치·선택과 좌우 패널 너비를 바꾸지 않는다. 오른쪽 설명의 실제 확인 결과는 그대로 읽을 수 있어야 한다.

드로어는 선택 모델의 제목·전체 행 수·모든 값·원래 ID와 정확한 참조 이름을 제공하며 내부 가로/세로 스크롤·고정 표 머리글·정확한 확인 행 강조를 유지한다. 모델별 표 스크롤과 드로어 열림 상태를 모델/업무 영역/확인 사항/상위 탭 전환에 보존한다. 숨겨진 표의 0 크기 때문에 복원 위치가 사라지지 않게 한다. 드로어의 닫기와 내부 Escape는 드로어만 닫고 열기 버튼으로 포커스를 돌린다. aria-expanded/aria-controls와 키보드 조작을 제공하며 표의 휠·드래그·텍스트 복사가 ERD 팬/줌으로 전달되지 않게 한다. 최소 중앙 너비·긴 제목·많은 속성·긴 값·빈 행·창 크기 변경에서도 조작과 모든 값에 접근할 수 있는지 확인한다. 미니맵의 독립적인 열림 상태와 좌표 이동은 유지한다.

샘플 드로어 위쪽 경계는 위/아래 드래그로 높이를 조절한다. 가로 separator와 aria 값, 위/아래 방향키·Home/End·Enter/두 번 클릭 기본 복귀를 제공한다. 사용자가 정한 높이는 닫기/열기·모델/업무 영역/확인 사항·상위 탭 전환에 유지하고 창 크기 변경 시 캔버스 안으로 제한하되 선호 높이는 기억한다. 도구 모음과 ERD 일부는 남겨 두며 높이 조절은 ERD SVG·카메라·선택·좌우 너비를 바꾸지 않는다. 드래그 중 텍스트가 선택되지 않고 포인터 취소·캡처 해제·닫기 후 조절 상태가 해제되어야 한다. 오른쪽 모델 상세 탭 이름은 **속성 | 설명**이다.

## 모델 JSON 가져오기와 내보내기

- 상단의 가져오기·내보내기는 모든 탭에서 제공한다. 기본 모델 JSON은 직접 작성/생성/공유 모두 지원한다. 현재 필터와 무관하게 전체 모델·설명·샘플·참조·기록된 확인 상태를 내보낸다. 기본 문서에는 체크섬·렌더러 핀이 필요 없다.
- 기본 문서의 검사는 모델 형식/스키마·standard 설명·전역 ID·관계/열·샘플 PK·확인 결과 대응·20MB 한계·JSON 문법이다. 실행 코드가 있는 중간 review.json은 build_model.py로 변환한다. JSON을 편집하면 재검사·가져오기만 하면 된다.
- 이전 data-modeling-share 파일에만 지원 렌더러/릴리스 해시·체크섬·내부 버전 일치 검사를 적용한다. 기존 공유 형식의 제약을 기본 모델 문서에 적용하지 않는다. 어떤 체크섬도 작성자 서명이나 실행 증명이 아니다.
- 오류/취소는 현재 데이터·선택·카메라를 유지한다. 성공 시 네 탭/ERD/샘플/참조/확인 상태를 한꺼번에 교체하고 이전 리스너·그림·관찰자를 해제한다. 같은 파일을 다시 선택할 수 있어야 한다.
- 모델 JSON과 기존 공유 파일은 종류를 구별해 표시한다. 통과/실패/미실행과 실행 결과 없음을 보존하고, 가져오기가 새 실행이 아님을 알린다. 다시 내보내면 원래 데이터와 선택 필드를 보존한다.
- 기존 뷰어 HTML을 수정하지 않고 현재 화면만 바꾼다. 공통 뷰어는 새로고침하면 빈 상태로 돌아간다. 새 업무마다 HTML을 만들거나 뷰어를 재생성하지 않는다. 성공/오류는 닫을 수 있는 상태 안내이며 모달/새 메뉴 행을 만들지 않는다.

## 공통 뷰어의 빈 시작 화면

- 유지보수/배포 시에만 `render_review.py --viewer --output model-viewer.html`로 같은 코드·CSS·스키마 검사기·배치 엔진을 묶는다. 배포본의 dist/model-viewer.html도 이 경로로만 생성한다. 빈 엔터티 배열이나 가짜 요구사항으로 standard 입력 검사를 우회하지 않는다.
- 내장 업무 데이터·샘플·실행 보고서·사례별 입력 해시는 없다. review/verification/build_metadata=null이며 뷰어 메타데이터와 라이선스는 포함한다. Python에서도 --viewer와 사례 입력/검증 옵션을 함께 쓰면 거부한다.
- 첫 화면은 한 화면의 간단한 사용 안내와 가져오기 버튼이다. 파일을 불러오기 전에는 보고서 탭·ERD·샘플을 만들지 않고 내보내기를 비활성화한다. 오류·파일 선택 취소는 빈 상태를 그대로 유지한다.
- 성공 후에는 기존 보고서와 같은 네 탭/ERD/속성/설명/샘플 드로어를 사용하고, 다른 업무 JSON으로 반복 교체할 수 있다. 생성된 별도 화면이나 사례별 분기를 만들지 않는다. 이후 내보내기도 원래 데이터/상태/버전을 보존한다.
- 새로고침하면 빈 시작 화면이다. localStorage/IndexedDB/자동 서버 전송으로 가져온 데이터를 남기지 않는다. 입력 JSON을 자동 수정하거나 SQL을 실행하지 않는다.

## 기본 모델 JSON의 직접 작성과 호환성

기본 데이터 계약은 model-1.0.0.schema.json이다. format/format_version/review만 필수인 문서로, review의 standard 업무 설명 요건은 유지한다. renderer_version/해시/SQL/expected는 작성하지 않는다. 선택 verification/build_metadata는 파일에 있는 내용대로 보존하며 없으면 미실행·생성 정보 없음으로 읽는다. 형식과 ID·관계·열·샘플 PK 검사는 직접 작성/생성/공유에 동일하게 적용한다.

이 기본 문서는 정상적인 JSON 편집으로 내용을 바꿀 수 있으며 체크섬을 다시 계산할 필요가 없다. 지원 형식과 review.schema_version이 같으면 선택 build_metadata의 생성기 버전을 이유로 거부하지 않는다. 기존 봉인 공유 형식의 체크섬/버전 검사는 별도 유지한다. 어떤 파일이든 로딩은 새 실행/사용자 합의/운영 검증이 아니다.

빈 뷰어는 직접 JSON 작성·스킬 생성·동료 공유를 모두 안내한다. 새 사례에서 뷰어나 독립 HTML을 만들지 않는다. build_model.py는 JSON만 생성하며 직접 작성 문서도 입력으로 받을 수 있고 HTML 확장자를 거부한다. render_review.py의 기본 JSON 출력도 build_model.py와 같은 함수/투영/검사를 사용한다. HTML은 --format html을 명시할 때만 생성하고 .html 파일명만 지정하면 거부한다.
