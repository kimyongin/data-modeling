# 업무 담당자를 위한 설명 작성

사례 데이터를 작성할 때 읽는다. 화면의 배치·탭·조작 규칙은 [뷰어 화면 계약](review-contract.md#기존-공통-뷰어의-화면-계약)이 정본이며 새 사례에서 변경하지 않는다.

## 비개발자도 판단할 수 있는 설명

보고서의 기본 독자는 데이터베이스를 모르는 업무 담당자다. **업무 상황 → 구체적인 예 → 왜 이렇게 관리하는지 → 확인할 질문** 순서로 설명한다. 전문 용어를 쉬운 동의어로만 바꾸지 말고 실제로 어떤 일이 달라지는지 풀어 쓴다.

- 처음 나오는 용어는 바로 뜻을 붙인다. 예를 들어 “반개구간” 대신 “10시~11시 예약이 끝나면 11시부터 다음 예약을 허용합니다”라고 설명하고, 필요한 기술 정의는 뒤에 남긴다. “복합 FK”만 쓰지 말고 “신청한 강의와 다른 강의의 수업이 연결되지 않도록 두 값을 함께 검사합니다”라고 쓴다.
- 각 정보 묶음에 무엇을 관리하는지, 표 한 줄의 의미, 실제 샘플에 맞는 예와 질문을 필요한 곳에 작성한다. `example`·`review_question`은 엔터티마다 반복할 필수 필드가 아니다. 항목에는 업무용 이름(`columns[].label`)과 값의 뜻을 적고 영문 필드명·타입·키는 보존한다.
- 관계를 만든 업무상 이유는 `relationships[].rationale`로 설명한다. 연결 방향·개수·키는 ERD에서 보고, 원래 열 대응·물리 정의는 재생성 입력에 보존한다.
- 검증은 `scenarios[].explanation`에 확인할 상황·예상 동작·확인 이유를 작성한다. 기본 모델 JSON은 기대 동작을 설명 문장으로 작성한다. 별도 실행 검증용 입력에서만 결과 열의 의미와 단위를 `result_columns`로 정의한다. 코드·JSON만 보고 성공 여부를 추측하게 하지 않는다. 잘못된 입력을 예상대로 막은 경우가 왜 통과인지 설명한다.
- 설명과 숫자는 샘플·규칙·실제 실행 결과에 맞아야 한다. 생성기는 용어 안내와 표시 형식을 제공하며 개별 업무 설명·성공 결과를 지어내지 않는다. 없는 설명은 미작성이라고 알리고 실패·미실행을 유지한다.
- 화면 문구도 쉬운 말로 쓴다. 요구사항의 범위 항목에는 업무별 읽는 순서를, 참조의 용어 안내에는 PK·FK·UQ·연결 개수의 뜻을, 그림에는 짧은 범례를 둔다. 확인 결과는 모델 탭의 업무 영역별 설명으로 제공하고 SQL·원시 실행 결과·비교 표·상세 펼치기를 HTML에 넣지 않는다. 설명을 추가하면서 새 요약 모드·자동 확대·추가 모달을 만들지 않는다.

완료 전에 비개발자의 입장에서 “무슨 상황인가, 왜 나눴는가, 예시 숫자가 무엇을 뜻하는가, 내가 무엇을 확인할 것인가”에 코드 없이 답할 수 있는지 직접 읽어 본다. 구조·행 수·콘솔 오류 검사를 통과한 사실만으로 설명이 친절하다고 판단하지 않는다.

## 스펙의 문맥과 간결함

- 요구사항은 원하는 동작을, `requirements[].design`은 그 동작을 위해 어떤 정보를 저장·연결·검사하는지 설명한다. 모델에 없는 기능을 약속하지 않는다. `example`은 실제 샘플에 맞는 짧은 예 하나다.
- 설계안은 여러 관련 결정을 업무 문장으로 엮는다. 결정 제목·이유·예시를 다시 카드로 반복하지 않고 관련 결정의 코드·제목과 판단 이유를 현재 본문에 텍스트로 표시한다. 기존 입력에 design이 없으면 직접 연결된 결정의 이유를 사용하고, 근거가 없으면 설명 미작성으로 남긴다.
- `review_points[].summary`는 현재 처리 범위 → 아직 정할 사항 → 바꾸면 필요한 설계를 1~2문장으로 정리한다. 이미 설계안에서 설명한 내용을 장황하게 반복하거나 선택지를 확정된 정책처럼 쓰지 않는다. 원래 질문·선택지·추천·영향은 재생성 입력에 보존하고 필요한 선택지와 제안은 현재 본문에서 읽는다.
- ‘현재 설계안 · 사용자 합의가 아님’ 같은 경고를 카드마다 반복하지 않는다. 검토 상태는 보고서 공통 영역에서 알린다. 단계 안내 화살표·빈 섹션·항목 수 나열·일반적인 성공 문장도 본문에서 걷어 낸다.
- 읽는 사람이 요구와 설계안의 관계, 구체 예, 아직 바꿀 수 있는 부분을 순서대로 이해하는지 실제 문장으로 검토한다. 항목 연결 검사만 통과했다고 문맥이 자연스럽다고 판단하지 않는다.

스펙은 모델의 설명 패널과 같은 제목·구분선·여백의 위계로 읽는다. 큰 구획은 **요약 → 설계안 → 남은 결정**을 유지하고, 설계안 안에서 업무 규칙·사용 예·설계 근거·관련 모델을 소제목으로 나눈다. 결정마다 코드: 제목과 선택 이유를 묶고 선택지의 이점/대가, 판단 기준/재검토 조건을 각각 이름 붙여 읽는다. 남은 결정의 선택지와 현재 제안도 해당 쟁점 안에서 구분한다. 내용을 접거나 별도 화면으로 보내지 않는다. 범위와 전제는 목표/범위·설계 선택·가정·미확인 사항·변경 영향을 같은 구획 방식으로 정리한다. 빈 구획을 채우기 위해 내용을 추가하지 않는다.

## 검토자가 판단할 수 있는 보고서

설계가 한다고 설명하는 일은 실제 항목·관계·처리 규칙·검증으로 뒷받침한다. 예를 들어 취소 상태를 남기는 것만으로 취소 사유·변경자·변경 이력을 추적한다고 쓰지 않는다. 근거가 부족하면 설명을 실제 보장 범위로 좁히거나 필요한 설계와 검증을 미결 사항으로 기록한다.

- 개요는 숫자와 보고서 사용 안내보다 설계의 큰 그림을 먼저 보여준다. overview에 문제·명시적 연결 그림·대표 사용 예·남은 핵심 판단을 직접 작성한다. 모델에 없는 기능이나 실제로 확인하지 않은 결과를 약속하지 않는다. 전체 범위·가정·핵심 설계 원문은 스펙의 범위와 전제에 보존한다.
- 검토 쟁점은 업무 정책 결정·범위 제외·실행 미검증을 구분해 질문·선택지·현재 추천안·결정에 따른 설계 영향을 작성한다. 엔터티 위험과 전제·제한을 대조해 빠뜨리지 않으며, 겹치는 위험은 관련 엔터티를 연결해 한 쟁점으로 묶는다. 제안과 실제 사용자 합의를 구별한다.
- 요구사항마다 직접 연결한 요구를 반영한 설계안·예시·남은 결정·관련 모델을 같은 본문에 보여주고 실제 확인 결과는 모델 탭에 연결한다. 여러 요구사항이 공유하는 판단은 한 원본으로 관리하고 각 요구사항에서 연결해 읽는다. 연결이 없는 결정·쟁점은 공통 사항 항목에 남기고 인과관계를 추측하지 않는다. 실행 통과는 해당 예시의 결과이며 요구사항 전체나 운영 준비가 확정됐다는 뜻으로 사용하지 않는다. 빠진 연결은 미작성으로 남긴다.
- 속성 탭은 짧은 역할 설명(`short_description`)·한 줄의 의미·항목 정의를 우선한다. 전체 설명·구체 예·질문은 기존 설명 탭에 보존한다. 1366×768에서도 첫 항목을 바로 읽을 수 있는지 확인한다.
- 업무 검토용 샘플은 서로 다른 의미를 설명하는 짧고 현실적인 행으로 구성한다. 장문·보안 문자열·대량 행은 별도 화면 경계 테스트 입력으로 둔다. 샘플을 바꾸면 의도한 예상 결과를 먼저 다시 계산하고 검증한다. 모든 행·긴 값은 여전히 생략 없이 내부 스크롤로 제공한다.
- 샘플에는 원래 ID를 유지하면서 정확하게 일치한 참조 행의 업무용 이름을 보조 표시한다. 확인할 수 없는 연결이나 여러 행과 일치한 값의 이름은 추측하지 않는다.
- 확인 결과는 모델 탭의 선택한 업무 영역에 맞춰 상황·기대 동작·관찰 결과로 보여준다. 실제 상태는 실행 보고서와 일치시키고, 예시 통과를 요구사항 전체나 운영 준비의 완료로 표시하지 않는다. SQL·원시 결과·비교 표·펼치기는 HTML에 넣지 않는다.
- 전문 용어를 풀어 쓸 때 요구사항·모델 이름·근거·예시까지 같은 업무 용어로 맞춘다. 화면 작동 검사에 더해 주장과 모델의 일치, 쟁점 누락, 첫 속성의 실제 노출과 예시 표의 행 높이를 직접 검토한다.


## 복잡도에 맞춰 분량 줄이기

- 단순한 사례는 핵심 요구·선택 이유·설계를 가르는 예 하나를 먼저 쓴다. 엔터티마다 같은 위험·전제·검토 질문을 복사하지 않는다.
- `design`과 `design_points` 중 하나를 택한다. 공통 판단은 decisions, 공통 전제는 assumptions/limitations에 한 번 쓰고 ID로 연결한다. 각 엔터티에는 그 엔터티만의 역할과 대가를 짧게 적는다.
- 1.1 standard는 업무용 이름·설명·한 행의 의미·항목 정의를 유지하고, 엔터티별 example/review_question/short_description/insights는 선택이다. 별도 위험이나 대가가 없으면 해당 설명을 생략하며 가짜 위험·대안·쟁점을 만들지 않는다. 복잡도가 높아도 전체 항목의 설명을 늘리지 말고 중요한 판단·예외·변경 경로를 깊게 검토한다.
- 검토 기록은 [설계 검토](design-review.md)의 ID 연결을 사용한다. 업무 설명을 extensions에만 숨기거나 검토 표를 스펙 본문에 복제하지 않는다.

확인 결과에는 방법과 범위를 함께 읽는다. 샘플 대조와 순차 시뮬레이션을 실제 API/DB/동시성 확인으로 설명하지 않는다. 예전 1.0 결과는 현재 입력 대응 미확인으로 표시한다. 모델의 role과 conditional inclusion은 기능 범위를 설명하며 위험 문장을 자동으로 정책 쟁점으로 승격하지 않는다.
