# 업무 담당자가 읽는 설명

사례 데이터를 작성할 때 사용한다. 데이터 필드의 정본은 [계약](review-contract.md)이며 화면 구현 세부사항은 [UI 지침](viewer-ui.md)에서 관리한다.

## 상황·예·이유를 연결하기

독자가 DB 전문 용어를 안다고 가정하지 않는다. “10시~11시 예약 뒤 11시부터 다음 예약을 허용합니다”처럼 실제 동작을 먼저 쓴다. 각 엔터티의 description은 무엇을 왜 관리하는지, grain은 한 행의 의미다. attributes.label과 description에는 업무용 이름과 값의 뜻을 쓴다. 구분 값·연결 값의 기술 정의는 유지한다.

관계의 description에는 연결의 업무 이유를, rule에는 지킬 조건을, enforcement에는 실제로 보장할 계층을 쓴다. 방향과 개수를 같은 문장으로 반복하지 않는다. 시나리오는 situation → expected_behavior → why_it_matters로 읽힌다. 기대 동작을 실제 관찰 결과처럼 쓰지 않는다.

설명이 주장하는 기능을 실제 모델·규칙·시나리오와 대조한다. 취소 상태만 남기면 변경자·사유·전체 변경 이력이 있다고 쓰지 않는다. 미확인 권한·원천 필드·동시성 보장을 설명으로 약속하지 않는다.

## 원문 한 곳, 연결은 ID

- requirements에는 원하는 동작을 쓴다. 실제 설계 조건은 rules, 비교와 선택 이유는 decisions에 한 번 쓴다.
- 규칙 title은 짧은 이름이고 statement는 지켜야 할 조건이다. 제목과 이유를 복사해 분량을 채우지 않는다.
- decisions에 선택지의 이점·대가·판단 기준·재검토 조건을 함께 쓴다. 선택한 안과 합의 상태는 다르다.
- issues에는 질문·선택지·추천·영향을 쓴다. 공통 가정·제한은 assumptions/limitations에 한 번 쓰고 변경 영향에서 연결한다.
- 변경 영향은 “무엇이 바뀌었나”와 “어떤 업무에 영향이 있나”를 구별한다. 확인한 전후 값을 before/after에 쓰고, areas에는 상태·모델·쟁점을 연결한다. 미기록과 영향 없음·미확인을 같은 뜻으로 설명하지 않는다. 공통 근거는 note_id 하나로 연결하고 각 영역에 같은 문장을 복사하지 않는다.
- 엔터티마다 가짜 위험·질문·대안을 채우지 않는다. 고유한 tradeoff/risk/example/question만 선택적으로 쓴다.
- 모델의 description에는 그 모델 고유의 역할과 필요한 이유를 쓴다. decisions의 대안 전체나 공통 정책을 다시 복사하지 않는다. 모델 설명은 선택 이유·대가와 현재 확인 사항의 관련 규칙을 조합하고, 대안 전체 비교는 스펙에서 읽는다. 이를 위해 rule.scenario_ids와 판단의 requirement_ids를 실제 관련 항목에 정확히 연결한다.

스펙은 요약 → 설계안 → 남은 결정으로 조합된다. 읽는 사람이 요구와 규칙·모델·선택의 관계를 문장으로 이해할 수 있는지 직접 검토한다. 항목 수나 연결 검사 통과만으로 친절한 설명이라고 판단하지 않는다.

## 개요와 샘플

개요의 diagram은 핵심 업무 정보와 명시적인 연결만 보여준다. PK/FK와 모든 속성으로 ERD를 복제하지 않는다. 목표·연결 의미·대표 사용 예·남은 판단은 모델이 지원하는 범위로 작성한다. 실제로 없는 선이나 기능을 지어내지 않는다.

샘플은 서로 다른 의미를 설명하는 짧고 현실적인 행으로 구성한다. 별도 데이터셋으로 상황을 구별하고 정확한 PK로 확인 행을 연결한다. 값이나 기대 동작을 바꾸면 실제 확인을 다시 수행하거나 결과를 제거한다. 모든 값은 내부 스크롤로 읽으며 별도 HTML·SQL·검증 탭을 만들지 않는다.

데이터셋 title은 ‘기본 업무 예시’, ‘이름 변경 후’처럼 무엇이 다른지 알려준다. 확인 사항에는 올바른 dataset_id를 연결한다. 업무 영역을 바꾸는 행위와 예시 데이터를 바꾸는 행위를 같은 의미로 설명하지 않는다.

완료 전에 “어떤 문제인가, 왜 나눴는가, 이 예시 숫자는 무슨 뜻인가, 무엇이 아직 미정인가”에 업무 언어로 답할 수 있는지 읽는다. 자료 형식·화면 구조·실제 구현 검사는 서로 구별해서 보고한다.
