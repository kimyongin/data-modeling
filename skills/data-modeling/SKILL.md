# 데이터 모델링

업무 질문에 답하고 예외·정정·변경에도 의미를 유지하는 데이터 모델을 설계한다. 기본 결과는 공통 뷰어에 가져올 모델 JSON이다. 설계 이유·대안·미확인 규칙과 변경 영향을 드러내고, 업무 담당자가 자기 언어와 샘플로 판단하게 한다.

## 범위와 원칙

- 새 설계·기존 개선·시스템 통합·분석 중 목적과 범위를 파악한다. 기존 명명·DB·도구·산출물 위치를 우선하고 미정인 DB의 물리 설계를 확정하지 않는다.
- 자료를 먼저 읽고 구조를 바꿀 불확실성만 질문한다. 작은 변경은 영향을 받는 요구·관계·시나리오만 갱신한다. 단계마다 승인을 반복하지 않는다.
- 사실·제안·가정·자료 충돌을 구별한다. 명시적으로 합의된 범위만 확정으로 기록하고 미결 정책은 남긴다. 모델에 없는 기능을 설명으로 약속하지 않는다.
- 합성·비식별 샘플을 사용하고 인증정보를 넣지 않는다. 조사·검토 권한을 운영 변경·배포 권한으로 확대하지 않는다.

## 1. 요구와 검토 깊이 정하기

업무의 사용자·행동·조회 질문·성공 기준을 안정적인 요구사항 ID로 정리한다. 대상의 동일성·소유권, 상태·시간·삭제·정정·집계, 기존 구조와 접근 패턴 중 설계에 영향을 주는 것을 확인한다.

[설계 검토](references/design-review.md)에 따라 단순(simple)·일반(standard)·복합(complex)과 이유를 정한다. 엔터티 수만으로 정하지 않는다. 금전·격리·이력·동시성·외부 원천 충돌·기존 데이터 전환이 판단을 바꾸면 해당 부분을 깊게 검토한다. 단순 사례에 모든 예외와 긴 설명을 강요하지 않는다.

## 2. 근거와 업무 규칙 조사

[조사·설계 기준](references/modeling-guide.md)의 관련 절을 읽는다. 연결 도구·로컬 자료·공식 원문을 확인하고 출처 위치·버전/확인일·지원하는 주장·한계를 남긴다. 접근하지 못한 관리자 화면을 조사했다고 쓰거나 예제 응답만으로 필수성·유일성·연결 개수를 확정하지 않는다.

규칙을 도출한 뒤 [누락 검토](references/design-review.md#업무-규칙의-누락-검토)를 수행한다. 규칙 하나마다 안정적인 ID를 두고 설계 반영 여부(modeled/unmodeled/excluded/not_applicable)와 합의 여부(proposed/agreed/open)를 따로 기록한다. 같은 영역의 여러 규칙을 하나로 뭉개지 않는다. 미정·제외·해당 없음을 구별하고 이유를 남긴다. 모델이 보장하는 범위와 별도 처리 계층에서 보장할 범위를 구별한다.

## 3. 대안을 비교하고 모델 설계

- 개념: 용어·대상의 경계·동일성·소유권·관계를 설명한다. 같은 이름을 같은 엔터티로 합치거나 모든 명사를 테이블로 만들지 않는다.
- 논리: 한 행/문서의 의미, PK·업무 키의 범위와 `unique_keys` 조합, 속성·필수성, 관계 양쪽의 개수, 참조·상태·이력·시간·삭제·정정 규칙을 정의한다.
- 물리: 요청 범위와 확인한 대상 DB에 맞춰 타입·제약·인덱스·전환 방법을 구체화한다. 논리 연결과 물리 FK를 구별하며 NoSQL에 관계형 DDL을 강요하지 않는다.

각 엔터티는 업무 핵심(core)·근거/운영 지원(supporting)·조건부 확장(optional)을 구별한다. 조건부 확장은 필요한 조건을 명시하고 현재 필수 구조처럼 설명하지 않는다.

모델을 바꾸는 핵심 선택은 현실적인 선택지별 이점·대가와 선택한 안을 구조화하고, 선택 기준·선택 이유·재검토 조건을 비교한다. 단순 사례는 논쟁할 대안이 없는 이유면 충분하다. 통합/전용/매핑, 정규화, 팩트/차원, 문서 내장은 목적에 맞춰 선택한다. 중복을 선택하면 갱신 주체·불일치 처리·허용 지연을 정한다.

[변경 영향](references/design-review.md#변경-영향-검토)을 확인한다. 기존 개선은 쓰기·조회·외부 계약·기존 데이터·과거 집계·전환·복구를 검토한다. 새 설계는 기존 전환을 해당 없음으로 두되 미결 정책이 달라질 때 무엇이 바뀌는지 남긴다. 비교 기준이 이전 설계 문서인지 실제 운영 스키마인지 명시하고, 추가·변경·제외한 엔터티/속성/관계의 전후와 요구사항을 기록한다. 문서 비교를 실제 데이터 이관 검증으로 해석하지 않는다. 현재 상태를 모르면 영향 없음으로 단정하지 않는다.

## 4. 설계를 가르는 샘플 작성

정상 상황과 실제 선택을 구별하는 경계 상황을 고르고 요구사항·모델·정확한 샘플 행을 연결한다. 상황·먼저 정한 기대 동작·확인 이유를 업무 문장으로 작성한다. [설명 작성](references/report-writing.md)에 따라 공통 설명은 한 번만 쓰고 각 항목의 고유한 의미를 남긴다.

기대 동작과 실제 관찰 결과를 구별한다. 샘플 대조·순차 시뮬레이션·실제 구현 확인·수동 검토·미실행의 방법과 범위를 기록한다. 같은 합계가 나와도 DB 제약·동시성·원천 완전성까지 확인했다고 쓰지 않는다. 실행 결과를 맞추려고 기대값을 바꾸지 않는다. SQL·검증 전용 탭은 기본 산출물에 추가하지 않는다.

## 5. JSON 작성 → 검사 → 기존 뷰어 확인

[직접 작성 안내](references/model-json.md)와 [완전한 예제](references/example-model.json), [데이터 계약](references/review-contract.md)을 따른다. UI 세부 지침은 해당 참조에만 두며 사례별 화면 코드를 만들지 않는다.

1. `references/schemas/model-1.1.0.schema.json`에 맞는 `<사례명>.model.json`을 작성한다. 새 사례는 standard이며 렌더러 핀·체크섬·SQL이 필요 없다.
2. `review.extensions.modeling_review`에 복잡도와 대안·규칙·변경 영향의 검토 연결을 작성한다. [검토 기록 계약](references/design-review.md#json-검토-기록)을 따른다. 설명 원문은 기존 decisions·review_points·assumptions/limitations에 한 번 작성한다.
3. `scripts/validate_model.py <사례명>.model.json`으로 구조·ID·검토 연결, 모든 샘플 행의 PK/필수 값/명시한 유일 조합/FK, 결과와 현재 입력의 대응을 검사한다. 생성기의 누락·중복 경고를 읽고 보완하거나 남은 한계로 명시한다. 경고가 없다는 사실을 업무 규칙의 완전성으로 해석하지 않는다.
4. 파일 정리에는 `scripts/build_model.py source.json --output <사례명>.model.json`을 쓴다. JSON과 생성 기록만 만들고 원문·선택 필드·실제 상태를 보존한다. 기존 실행 자료의 선택 변환은 [생성 절차](references/rendering-workflow.md)를 따른다.
5. 동봉된 `assets/model-viewer.html`에서 JSON을 가져와 설명·ERD·샘플을 읽는다. 사례마다 HTML을 만들거나 뷰어를 재생성하지 않는다. 결과 JSON·스킬에 동봉된 뷰어 위치·중요한 판단과 실제 확인 범위·남은 결정을 전달한다.

verification은 생략/null이면 미실행이다. 실제 확인한 결과에만 방법·범위와 review 내용 지문을 기록한다. 새 형식은 내용 변경 후 이전 결과가 남으면 거부한다. 다시 수행하지 않았다면 결과를 제거하거나 `--clear-verification`을 명시한다. 생성기가 임의로 성공 기록의 지문만 새로 찍지 않는다. 뷰어도 같은 검사로 거부하며 새로 실행한 결과처럼 표시하지 않는다. 이전 1.0 파일은 그대로 읽고 결과는 입력 대응 미확인인 과거 기록으로 구분한다. 명시적 이전과 결과 기록은 [내용 대응 계약](references/result-integrity.md)을 따른다. 기존 파일은 새 검토 기록 없이도 호환되며 새 사례의 검토 절차는 생략하지 않는다. 미작성 보존용 compatibility를 새 사례의 설명 생략 수단으로 사용하지 않는다.

## 유지보수 작업

스킬에는 JSON 작성·검사·이전 도구와 완성된 뷰어가 동봉되어 있다. 새 사례 때문에 뷰어를 빌드하지 않는다. JSON 검사는 뷰어 코드·개발 도구·뷰어 릴리스 해시에 의존하지 않는다.

사용자가 스킬·생성기·화면 개선을 요청하면 개발 저장소의 dev 도구와 검사를 사용하고, 동봉 뷰어·설치본·배포 ZIP을 함께 확인한다. UI 구현 원본은 개발 영역에 두며 설명 작성은 [문장 지침](references/report-writing.md)을 따른다. 데이터 계약의 변경에는 새 버전과 명시적인 이전을 제공하고 이전 스키마·릴리스는 보존한다.
